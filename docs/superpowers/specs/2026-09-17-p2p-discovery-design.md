# P2P 发现与连接设计（专项）

- 日期：2026-09-17
- 状态：待评审
- 关联文档：[p2pSync 总体设计](./2026-09-17-p2psync-design.md)

本文档是整个项目的技术核心：**在完全不部署服务器的前提下，两个（或多个）互不相识的客户端如何找到彼此并建立 P2P 连接**。

## 1. 问题定义

WebRTC 建立直连需要解决三个问题：

| 问题 | 说明 | 对应技术 |
|------|------|----------|
| **发现** | 双方互相不知道对方的存在与地址，如何"找到组织" | 信令：通过一个双方都能访问的"公告板"交换连接信息 |
| **穿透** | 双方大概率都在 NAT/防火墙后面，如何打通一条可达路径 | ICE + STUN（必要时 TURN） |
| **传输** | 路径打通后如何可靠传输同步消息 | WebRTC DataChannel（SCTP over DTLS） |

传统方案中"发现"由自建信令服务器（WebSocket 房间）完成，本项目约束是不部署服务器，因此信令必须借助**第三方公共基础设施**。

## 2. 信令方案选型

### 2.1 候选方案对比

| 方案 | 原理 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **Trystero（nostr 策略）** | 将房间 ID 派生为 Nostr 订阅主题，在多个公共 Nostr 中继上发布/订阅加密信令消息 | 零部署、零账号；多中继并行，单点故障风险低；中继只看到加密数据 | 依赖公共中继可用性 | **✅ 采用（主方案）** |
| Trystero（tracker 策略） | 房间 ID 派生为 infohash，向公共 BT tracker announce 完成互相发现 | 零部署；tracker 在国内可达性较好 | 公共 tracker 数量在减少，稳定性参差 | 备选回退策略 |
| PeerJS 公共云 | PeerJS 官方免费信令服务器 | 简单 | 单点依赖、免费服务无 SLA、境外节点国内不稳定 | ❌ 不采用 |
| Firebase/Supabase 实时库 | 用云厂商免费额度做信令 | 稳定 | 需要注册账号、配置项目，违背"开箱即用" | ❌ 不采用 |
| 手动复制粘贴 SDP | 双方手动交换 offer/answer 文本 | 绝对零第三方依赖 | 每次连接要来回粘贴两次以上，多人场景不可用 | ❌ 不采用（仅作为最后兜底思路记录） |

### 2.2 决策

采用 **Trystero 的 nostr 策略为主，tracker 策略为备选回退**。理由：

1. 零部署、零账号，`npm install trystero` 即可使用
2. nostr 策略可同时配置多个公共中继，任一中继可达即可完成信令，天然容错
3. Trystero 对信令消息做了端到端加密（以房间信息派生密钥），中继方无法读取连接元数据以外的内容
4. 连接建立后一切数据走 P2P DataChannel，中继不再参与

## 3. 房间发现机制设计

### 3.1 房间 ID 生成

```ts
/**
 * 生成房间 ID
 * 使用 crypto.getRandomValues 取 10 字节随机数，编码为 16 字符 Base32 字符串。
 * 约 80 bit 熵：防碰撞（两人同时建房重复概率可忽略）、防撞房（不可被猜测进入）。
 * 返回值：如 "K7Q2M9XT4P1WVBEH" 的 16 字符大写字母数字串
 */
export function generateRoomId(): string
```

### 3.2 信令主题派生

Trystero 通过 `appId + roomId` 共同确定信令主题：

- `appId = "p2psync-v1"`：应用命名空间，防止与其他 Trystero 应用串台
- `roomId`：房间唯一标识
- 版本号编入 appId（`v1`），未来协议不兼容时切换命名空间，新旧版本互不干扰

### 3.3 加入房间的完整时序

```
房主 A                         公共 Nostr 中继                    成员 B
  │                                │                               │
  │ 1. 创建房间 generateRoomId()   │                               │
  │ 2. joinRoom(appId, roomId)     │                               │
  │─────── SUBSCRIBE 订阅主题 ─────▶│                               │
  │                                │                               │
  │                                │        3. B 打开分享链接       │
  │                                │        4. joinRoom(appId, roomId)
  │                                │◀────── SUBSCRIBE 订阅主题 ─────│
  │                                │                               │
  │◀───── 中继转发 B 的加密 offer ──│◀────── PUBLISH offer ─────────│
  │ 5. WebRTC setRemoteDescription │                               │
  │────── PUBLISH 加密 answer ─────▶│────── 中继转发 answer ───────▶│
  │                                │                               │
  │ 6. 双方并行进行 ICE 打洞（见第 4 节，不经过中继）                  │
  │══════════════ DataChannel 建立（P2P 直连）════════════════════▶│
  │                                │                               │
  │ 7. Trystero 触发 onPeerJoin                                    │
  │◀─────────── hello（请求全量状态）───────────────────────────────│
  │──────────── state（视频URL/位置/播放状态）─────────────────────▶│
  │ 8. 成员导航到视频页，进入同步循环                                  │
```

关键点：

- 步骤 1~5 仅信令元数据经过中继，且为端到端加密，中继无法窥探内容
- 步骤 6 起中继完全退出，视频页面地址、播放进度等业务数据全部走 P2P 直连
- 第 3 个及以后的成员加入流程相同，Trystero 自动维护全网状（mesh）拓扑：每个成员与房间内其他所有成员各建立一条 DataChannel

### 3.4 Trystero 接入设计（core/room.ts）

```ts
import { joinRoom } from 'trystero/nostr'

/**
 * 加入（或创建）一个同步房间。
 * 本函数是 Trystero 的唯一封装入口，其余模块不直接接触 Trystero API，
 * 便于未来更换信令策略或自建信令时只改这一个文件。
 *
 * 参数：
 * - roomId: 房间 ID（房主为生成值，成员来自分享链接）
 * - role: 'host' | 'follower'，用于日志与回调语义区分（Trystero 本身无角色概念）
 * 返回值：
 * - 房间句柄，含发送/接收消息与成员事件订阅能力（详见 core/protocol.ts）
 */
export function openRoom(roomId: string, role: 'host' | 'follower') {
  const config = {
    appId: 'p2psync-v1',
    // STUN 服务器：国内外混合列表，提高各类网络环境下的打洞成功率
    stunServers: [
      'stun.l.google.com:19302',      // Google（境外）
      'stun.cloudflare.com:3478',     // Cloudflare（境外）
      'stun.qq.com:3478',             // 腾讯公共 STUN（境内）
      'stun.miwifi.com:3478',         // 小米公共 STUN（境内）
    ],
  }
  return joinRoom(config, roomId)
}
```

> 注：`stunServers` 若 Trystero 版本不支持该配置名，则改用 `rtcConfig.iceServers` 传入，以接入时实际验证为准。

### 3.5 分享地址与连接建立

- 房主创建房间后生成：`p2psync://join?room=<roomId>&url=<视频页地址>`
- 成员端唤起流程：
  1. 操作系统根据自定义协议唤起应用（主进程 `setAsDefaultProtocolClient('p2psync')` 注册，`open-url` / 第二实例事件接收 URL）
  2. 主进程解析参数，交给渲染进程
  3. 渲染进程调用 `openRoom(roomId, 'follower')`，同时用 WebContentsView 打开 `url` 对应视频页
  4. 收到房主 `state` 消息后，注入脚本将视频 seek 到指定位置并跟随播放状态

## 4. NAT 穿透（ICE/STUN）设计

### 4.1 原理简述

ICE 流程中，双方各自收集候选地址（candidate）并交换（该交换复用信令通道）：

- **host candidate**：本机局域网地址（同一局域网时直接命中，直连最快）
- **srflx candidate**：通过 STUN 服务器探测到的公网映射地址（打洞的目标）
- **relay candidate**：TURN 中继地址（本项目 P0 不配置）

拿到对方公网映射地址后，双方同时向对方发包在 NAT 上"打洞"，成功后路径固化，DataChannel 在其上传输。

### 4.2 可达性预期

| 网络组合 | 打洞结果 | 说明 |
|----------|----------|------|
| 同一局域网 | ✅ 直接 host candidate 直连 | 无需公网 |
| 家庭宽带 × 家庭宽带 | ✅ 绝大多数可打通 | 家用路由器多为锥形 NAT |
| 家庭 × 手机热点 | ✅ 大多数可打通 | 运营商热点多为端口受限锥形 NAT，仍可打洞 |
| 双方均为对称 NAT（部分企业网/运营商级 NAT） | ❌ 可能失败 | 需 TURN 中继，P1 处理 |

### 4.3 失败检测与用户反馈

P0 必须让用户明确知道"为什么连不上"：

- 监听 WebRTC 连接状态（经 Trystero 的事件或底层 peerConnection 状态推断）：
  - `connecting` 超过 15 秒未建立 → 判定连接失败
  - 连接状态进入 `failed` → 判定打洞失败
- UI 明确提示："NAT 穿透失败，请尝试切换网络（如改用手机热点）"，并说明该限制的原理
- 房主端保留成员加入超时提示："分享链接后无人加入？请检查双方网络"

## 5. 连接拓扑与扩展性

- Trystero 维护**全网状（mesh）拓扑**：N 人房间共 N×(N-1)/2 条 P2P 连接
- 房主权威模型下消息量极小：心跳 1 条/2 秒/房主，事件消息仅在操作时产生，mesh 在 **10 人以内**完全没有压力
- P0 限制房间人数上限 8 人（UI 提示），避免极端场景下的 mesh 连接开销；P1 如需更大房间再引入星型拓扑（成员消息经房主转发）

## 6. 断线与容错

| 场景 | 处理 |
|------|------|
| 成员中途掉线 | `onPeerLeave` 触发 → 更新成员列表；该成员重开链接后重新走加入流程 |
| 房主中途掉线 | 成员端检测到与房主的连接断开 → UI 提示"房主已离开"；P0 不做房主迁移，P1 实现选举 |
| 信令中继不可达 | 已建立连接不受影响（中继只在建连阶段参与）；新成员建连失败时 Trystero 内部对多中继并行尝试 |
| 本地网络切换（WiFi ↔ 热点） | ICE 会自动重启尝试恢复；无法恢复则按掉线流程处理，用户重新点链接即可 |

## 7. 安全设计

1. **传输加密**：WebRTC DataChannel 强制 DTLS 加密，明文不可能在 P2P 链路上传输
2. **信令加密**：Trystero 以房间信息派生密钥加密信令载荷，公共中继只能看到不可读的密文
3. **房间准入**：roomId 即准入凭证（80 bit 熵），未持有链接的人无法发现房间；P1 可增加房间口令
4. **输入边界**：分享链接中的 `url` 参数在成员端打开前校验协议（仅允许 `http/https`），防止任意协议注入

## 8. 验证计划（本专项）

1. **单元级**：roomId 生成熵与格式、链接编解码往返一致性
2. **本机联调**：同机两实例（不同 userData）→ 验证 host candidate 直连与消息互通
3. **跨网络联调**：家庭宽带 × 手机热点 → 验证 srflx 打洞、心跳同步、掉线重连
4. **信令容错**：人为屏蔽部分中继域名 → 验证剩余中继仍可建连
5. **失败路径**：模拟对称 NAT（企业网/受限网络）→ 验证 15 秒超时判定与 UI 提示
